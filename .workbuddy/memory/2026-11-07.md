# 2026-11-07

## GitHub Actions 支持按日期发 Release

- `.github/workflows/release.yml` 从「仅 release: published」扩成三触发：`schedule`（每天 00:05 北京时间）+ `workflow_dispatch`（可填 tag、可 force）+ `release: published`（沿用原行为，只传附件不改标题/说明）。
- cron 用 UTC `5 16 * * *`（= 次日 00:05 北京），日期用 `TZ=Asia/Shanghai date +%Y.%m.%d`，tag 形如 `v2026.11.07`。
- 跳过逻辑：当天已发过该 tag → 跳过；自上一个 release 以来没有 `*.yaml|*.yml` 变化 → 跳过（`::notice::`，不算失败）。`force` 可绕过。
- 关键坑（都已在脚本里处理）：`gh release list -q '.[0].tagName'` 在无 release 时输出字面量 `null` → 用 `// ""` + 再兜一次；上一个 release 的 tag 本地不存在时清空，否则当 `previous_tag` 传给 API 会 422；同一天重发靠 `overwrite_files: true` 覆盖附件。
- 校验：本地用 7 个场景跑过 meta 脚本（无 release / 有改动 / 当天已发 / force / 指定 tag / release 事件 / tag 不存在），行为符合预期；打包脚本在 /tmp 副本里跑通，10 个目录各出一个 zip。
- 注意 GitHub 会在仓库 60 天无提交后停用定时工作流（发 release 不算活跃）。

### 修正：去掉定时触发（用户要求）

- 移除了 `schedule` / cron，也不再需要 `force` 输入与「无变化跳过」逻辑；现在只有 `workflow_dispatch`（tag 留空 = 当天 `vYYYY.MM.DD`）和 `release: published` 两种触发。
- 手动运行一律打包发布；同一 tag 重复跑靠 `overwrite_files: true` 覆盖附件；`previous_tag` 仍取上一个 release（相等时置空，避免自己比自己）。
- 脚本里把 `[ cond ] && action` 改成 `if` 块，避免 `set -e` 下 AND-list 返回非零的边界问题。

### 修正：日期 tag 去掉 v 前缀（用户要求）

- `tag="v$(TZ=Asia/Shanghai date +%Y.%m.%d)"` → `tag="$(TZ=Asia/Shanghai date +%Y.%m.%d)"`，即 `2026.11.07` 这种形式。
- 同步改了 workflow 头部注释、`tag` 输入的 description、README「发布」表格里的示例。
- `release: published` 与手动填写的 tag 原样使用，不做前缀增删。
- 注意：本仓库目前本地没有任何 tag，远端 release 情况未能确认（gh 未登录，401）；若已有 `v*` 旧 release，新日期 tag 与之并存不影响 `previous_tag`（只要求 git 能解析到该 ref）。
